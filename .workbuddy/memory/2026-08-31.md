## 第四轮：补端到端测试（补「零实跑验证」这个窟窿）

### 设计

- 极简 HTTP 服务器 `TestServer`：`TcpListener::bind("127.0.0.1:0")` 取随机端口，
  每个连接 spawn 一个任务，`serve_once` 读到 `\r\n\r\n` 就停，按请求路径查 HashMap 返回预设内容。
  不实现完整 HTTP 语义（不管 Header、Range、keep-alive），够驱动下载核心即可。
- `ts_segment(packets, fill)` 造 TS 数据：188 字节包、首字节 0x47，填充值按分片区分，
  合并后逐字节比对即可校验顺序正确。
- `test_settings()` 关掉 ffmpeg（测试机未必装了，且会让输出路径不确定）与尾部加速，
  并保留临时文件以便断言分片落盘。
- 5 个用例：TS 下载合并 / AES-128 解密合并 / 主播放列表选最高带宽 / 分片级断点续传 / 404 干净失败。
- 断点续传的验证技巧：只给前 2 个分片配路由，第 3 个预置成哨兵数据（填充 0x7e）写进任务目录。
  若该分片被重新下载就会 404 让任务失败；末尾比对到哨兵数据即证明跳过了。

### 进度事件流也纳入覆盖

GUI 只靠 `TaskEvent::Snapshot` 刷新，事件流断了界面就是静止的。新增 `run_download_with_events`
收集全部快照，在 TS 用例中断言：过程中出现过 Downloading、progress 单调递增无回跳、
最后一个快照是 Completed 且进度 100%。`run_download` 保留原签名，委托给它。

### 踩坑：IV 字面量写错

AES 用例一开始失败，报 `任务执行失败: InvalidPlaylist`。加临时 println 确认 M3U8 文本本身没问题，
用 python 统计才发现 IV 的 hex 部分是 **34 字符（多写了一组 `7c`）**，而 `parse_iv` 要求严格 32 字符。
**是我测试数据写错，不是产品代码的 bug**——`parse_iv` 正确拒绝了非法 IV。

修法不是改字面量，而是让 IV 由加密用的字节数组生成：

```rust
let iv_hex: String = iv.iter().map(|byte| format!("{byte:02x}")).collect();
let key_line = format!("#EXT-X-KEY:METHOD=AES-128,URI=\"/key.bin\",IV=0x{iv_hex}");
```

这样「加密用的 IV」和「播放列表里的 IV」在结构上不可能不一致。
教训已写进 AGENTS.md：测试里不手写十六进制常量。

## 第五轮：修复托盘菜单「点击无效」（用户报 bug）

用户反馈：`cargo run` 时托盘右键两个选项点了都无效，点退出很久才退出。

### 排查：加临时诊断 + 用户跑一次拿输出

在 `TrayController::poll` 打事件 id、在 `process_tray` 打动作、在 `update` 每 500ms 打一帧。
**诊断输出推翻了最初假设**：事件其实收到了，id 也匹配正确，帧循环也在跑（`minimized=false`）。
日志里 `Exit` 出现两次，是用户等不及又点了一次。

### 根因（两条叠加）

1. **空闲时 1000ms 才重绘一帧**（`update` 末尾 `request_repaint_after`，idle=1000ms），
   而 `poll()` 每帧只 `try_recv` **一个**事件。连点几次就排到后面几帧，延迟叠加成「很久」。
2. **「显示主窗口」在窗口已可见时没有任何可见效果**——只做了 `Minimized(false)` + `Visible(true)`，
   窗口若在别的窗口背后就看不出变化，用户判定「无效」。

### 修复（`src/app/tray.rs` + `src/app/mod.rs`）

- 改用 `MenuEvent::set_event_handler(Some(closure))` 回调替代每帧轮询 channel，
  回调里把动作推进 `Arc<Mutex<VecDeque<TrayAction>>>`，然后 `ctx.request_repaint()` **立即唤醒事件循环**。
  延迟从最长 1000ms 降到毫秒级。
- `poll() -> Option<TrayAction>` 改为 `take_actions() -> Vec<TrayAction>`，一次排空，延迟不再累积。
- 抽出 `restore_window()`：`Minimized(false)` + `Visible(true)` + **`ViewportCommand::Focus`**，
  确保窗口真的被带到前台。
- 顺带修掉一个真缺陷：原 `Exit` 分支在窗口最小化时直接 `std::process::exit(0)`，
  **绕过了「有下载任务时退出需确认」**。现在确认逻辑一律优先，只在确认可关闭且窗口最小化时才 exit(0)。

### 关键机制（查 muda/eframe 源码得来，下次别再猜）

- `muda` 靠 `SetWindowSubclass` 拦截 `WM_COMMAND` 才发出菜单事件；`tray-icon` 在构建时
  调 `attach_menu_subclass_for_hwnd` 挂上，所以事件链路本身是通的。
- `MenuEvent::set_event_handler` 与 `MenuEvent::receiver()` **互斥**：设了 handler 就不再进 channel。
  且 muda 用 `OnceCell` 保存，**必须在首次菜单事件之前注册**，否则永远装不上。
- eframe 0.29 在 `wgpu_integration.rs` / `glow_integration.rs` 里注册了
  `set_request_repaint_callback`，回调经 `EventLoopProxy::send_event(UserEvent::RequestRepaint)`
  唤醒事件循环。所以 `ctx.request_repaint()` 是可靠的立即唤醒手段。
- `ViewportCommand::Focus` 在 egui 0.29 是**单元变体**，写 `Focus(true)` 会编译报错。
- `set_event_handler` 的闭包参数类型推断不出来，要显式标 `move |event: MenuEvent|`。
